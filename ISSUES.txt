ISSUE B-5 [ACTIVE] — No multer error handler middleware
--------------------------------------------------------------------------------
File:    backend/src/routes/messageroutes.js (Line 17)
         backend/src/index.js
Status:  ACTIVE — silent failures for oversized / wrong-type uploads
Detail:  When multer rejects a file (wrong mimetype or size > 30MB), it calls:
           cb(new Error("only images and video uploads are allowed"))
         But there is no Express error-handling middleware (4-arg function) to
         catch this. Express will either hang the request or send a generic 500
         with no useful message back to the frontend.
Fix:     Add an error-handling middleware after route registration in index.js:
           app.use((err, req, res, next) => {
             if (err.message?.includes("images and video")) {
               return res.status(415).json({ message: err.message });
             }
             if (err.code === "LIMIT_FILE_SIZE") {
               return res.status(413).json({ message: "File too large (max 30MB)" });
             }
             next(err);
           });

ISSUE B-6 [ACTIVE] — Message model has no validation: all fields can be null
--------------------------------------------------------------------------------
File:    backend/src/models/message.js
Status:  ACTIVE — DB can store empty messages
Detail:  The schema has no "required" constraint on text, image, or video.
         A message with all three fields empty/null can be saved to MongoDB.
         The controller does not validate that at least one field is present.
Fix:     Add a pre-validate hook in message.js:
           messageSchema.pre("validate", function(next) {
             if (!this.text && !this.image && !this.video) {
               next(new Error("Message must have text, image, or video"));
             } else {
               next();
             }
           });

ISSUE B-7 [ACTIVE] — connectDB() called INSIDE server.listen() callback
--------------------------------------------------------------------------------
File:    backend/src/index.js (Lines 47-52)
Status:  ACTIVE — minor race condition, not a crash risk in practice
Detail:  connectDB() is invoked inside the server.listen() callback. This means
         the server starts accepting HTTP connections BEFORE the database
         connection is established. Any request that arrives in that small window
         will fail with a Mongoose "not connected" error.
Fix:     Call connectDB() first, then start the server:
           await connectDB();
           server.listen(PORT, () => { ... });
         (Requires wrapping in an async IIFE or top-level await.)

ISSUE B-8 [ACTIVE] — Clerk Webhook not reachable on localhost
--------------------------------------------------------------------------------
File:    backend/src/webhooks/clerk.js
         backend/src/middleware/authmiddleware.js (Line 21)
Status:  ACTIVE — new user sign-ups break locally without a tunnel
Detail:  Clerk sends webhook events (user.created) to a public URL. On
         localhost:3000, Clerk cloud cannot reach the server. If the webhook
         is not received, the MongoDB User document is never created.
         protectRoute then returns HTTP 404 "user profile is not synced yet"
         and ALL API calls fail for that user.
Fix:     Use the Clerk CLI or ngrok to forward webhooks during development:
           npx @clerk/dev-server   OR   ngrok http 3000
         Then update the Clerk Dashboard webhook URL to the tunnel URL.

ISSUE B-9 [ACTIVE] — Cron job pings FRONTEND_URL for /health (wrong target)
--------------------------------------------------------------------------------
File:    backend/src/lib/cron.js (Lines 7-9)
Status:  ACTIVE — wrong URL target
Detail:  The cron job builds the health check URL from process.env.FRONTEND_URL:
           const url = new URL("/health", base).href;
         But /health is a BACKEND route (defined in index.js), not a frontend
         page. In production this would ping the frontend server for /health,
         which returns an HTML 404, not the JSON { ok: true } response.
Fix:     Add a BACKEND_URL env variable and use it here:
           const base = process.env.BACKEND_URL || `http://localhost:${process.env.PORT || 3000}`;
         Or simply ping the backend's own internal port.

ISSUE F-1 [ACTIVE] — Optimistic message fallback hides real upload failures
--------------------------------------------------------------------------------
File:    frontend/src/store/useChatStore.js (Lines 100-117)
Status:  ACTIVE — UX problem, masks failures silently
Detail:  When sendMessage() throws (e.g., backend returns 500), the catch block
         creates an "optimistic" local message using the blob previewUrl. This
         makes it LOOK like the message sent (with image) even though it was
         NOT saved to the DB. The message disappears on page refresh.
         A toast shows "Message delivery failed" but the fake message stays.
Fix:     Do NOT add an optimistic message in the catch block when a file was
         attached — only show the toast error:
           if (!messageData.file) {
             set({ messages: [...messages, optimisticMsg] });
           }
           toast.error(...);


--------------------------------------------------------------------------------
ISSUE F-2 [ACTIVE] — File cleared (blob URL revoked) before upload completes
--------------------------------------------------------------------------------
File:    frontend/src/components/chat/ChatComposer.jsx (Lines 52-55)
Status:  ACTIVE — timing issue with blob URLs
Detail:  In handleSend():
           removeFile();            // revokes blob URL + clears state
           await sendMessage(...);  // sends file (still works via closure)
         The file ref inside messageData is a closure so the upload works.
         But the previewUrl blob is REVOKED before the request settles.
         The optimistic fallback in useChatStore's catch block then tries to
         render messageData.previewUrl which is already invalid.
Fix:     Move removeFile() to run AFTER sendMessage resolves:
           const result = await sendMessage(messageData);
           if (result) removeFile();

ISSUE F-4 [ACTIVE] — Socket connection does not guard against undefined userId
--------------------------------------------------------------------------------
File:    frontend/src/store/useAuthStore.js (Line 37)
Status:  POTENTIAL BUG — online status and real-time delivery silently break
Detail:  Socket connection passes: { userId: user._id }
         MongoDB documents use _id. If the authUser object ever lacks _id
         (e.g., network timing or field differences), userId=undefined is sent.
         The backend userSocketMap then stores undefined as the key, making
         real-time message delivery and online status silently not work.
Fix:     Use: { userId: user._id || user.id }
